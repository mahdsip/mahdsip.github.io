Architectural styles and patterns

Theoretical styles and practical patterns I have worked with

Although I have spent the last few years focused on data exploitation, throughout my professional career I have had the privilege of working with different architectures such as SOA, BPM, Cloud Computing and Java.

There are many ways to classify architectural styles. They are distinguishable from architectural patterns in that styles are purely theoretical while patterns are purely practical — and several can be combined within a single architecture.

Architectural styles

Data flow styles:

  • Pipes and filters (transformation of a data stream with a final result)
  • Batch processing (batch jobs and scripts)

Data-centred styles:

  • Blackboard or repository
  • Database
  • Hypertext

Call and return styles:

  • Layered (MVC)
  • Object orientation
  • Component-based

Mobile code styles:

  • Virtual machines (compiled code)
  • Interpreters (interpreted code)

Heterogeneous styles:

  • Process control
  • Attribute-based (reasoning over quality attributes)

Peer-to-Peer styles:

  • Event-based (invoking a function when a Publisher/Subscriber event occurs)
  • SOA — A call is made to a service passing the required parameters and a result is expected. SOA 2.0 = SOA + events.
  • Resource-based. Resources can be discovered via a URI and their state retrieved to operate on them.

Cloud computing

  • Private cloud: The organisation retains tighter control over infrastructure, security, network segmentation and service lifecycle. Usually the right fit when there are strong internal integration requirements, compliance constraints, sensitive data, or a need to adapt the platform heavily to internal processes.
  • Public cloud: The main advantages are faster provisioning, elasticity and access to managed services that accelerate both development and operations. The key is to design cost control, observability, security and vendor dependency carefully so that the initial flexibility does not turn into operational debt.

Architectural patterns

Architectural patterns are reusable, proven solutions to recurring problems in software design. Unlike styles, they are concrete and directly applicable. The most common ones in modern development:

Singleton
Ensures that a class has only one instance throughout the application's lifecycle and provides a global access point to it. Widely used for configuration managers, database connections and shared caches. Its main risk is introducing global state that makes testing and concurrency harder.

Factory / Abstract Factory
Delegates object creation to specialised methods or classes, decoupling the client code from the concrete type being instantiated. Common in persistence frameworks and UI component creation.

Observer / Pub-Sub
Defines a one-to-many dependency between objects: when one changes state, all its observers are notified automatically. It is the foundation of event systems, message queues and reactive programming.

Strategy
Encapsulates a family of interchangeable algorithms behind a common interface, allowing behaviour to vary at runtime without modifying the code that uses it. Very useful in rule engines, validators and processing pipelines.

Decorator
Adds responsibilities to an object dynamically by wrapping the original implementation without altering its interface. The basis of HTTP middlewares and interceptors in frameworks like Spring or Express.

Repository
Abstracts data-layer access behind a domain-oriented interface, isolating business logic from persistence details (SQL, NoSQL, remote API). Fundamental in DDD and Clean Architecture.

API (Application Programming Interface)
An API defines the contract through which external clients consume an existing service. The provider defines the interface and implements it. It is the standard mechanism for interoperability between systems: REST APIs, GraphQL, gRPC and SDK libraries are all examples. A well-designed API is stable, versioned and hides internal implementation details.

SPI (Service Provider Interface)
The SPI is the inverse pattern to the API. The system's core defines an interface that third parties implement to extend or replace its behaviour, without modifying the central code. It is the fundamental mechanism behind plugin architectures and Inversion of Control (IoC).

Relationship with architecture:

  • Plugin architecture: SPI allows the core of an application to remain intact while third parties extend its functionality.
  • Inversion of Control (IoC): The main system defines the rule (the interface), but the concrete implementation is provided by a third party and loaded dynamically at runtime.
  • Strict decoupling: Completely separates service providers from service consumers, promoting the single responsibility principle.

Key difference: API vs. SPI

Concept Purpose Who defines it Who implements it
API The means for clients to consume an existing service The service provider The service provider
SPI The means for developers to replace or extend a service The system core or client The external provider (third parties)

Common usage examples:

  • Java (JDBC): Java defines the SPI for databases (java.sql.Driver). Companies like Oracle, MySQL or PostgreSQL implement that SPI so their drivers work in any Java application without changing the source code.
  • Logging systems: Tools like SLF4J expose an SPI so you can switch between log providers (Logback, Log4j) transparently.
