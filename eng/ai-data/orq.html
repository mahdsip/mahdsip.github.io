Orchestration and choreography

Two approaches to service composition

Both approaches deal with composing services to solve a business problem. The main difference is scope and where the coordination lives.

Orchestration

An executable business process runs on a central engine that invokes each participating service in the right order. There is a middleware component (the engine) acting as conductor.

The most common notations and languages are:

  • BPMN (Business Process Model and Notation), standardized by the OMG. From version 2.0 the diagrams can be serialized to executable XML that runs on a BPMN 2.0 engine such as Activiti.
  • BPEL (WS-BPEL), an OASIS standard focused on orchestrating web services through an explicit control flow.

Choreography

Peer-to-peer collaboration between services with no central middleware. Each participant knows the interaction rules and reacts to the messages it receives. It defines the joining and cooperation rules between peers.

The main standardization effort in this area was OASIS's WS-CDL (Web Services Choreography Description Language). SCA also fits the choreography model naturally, since the entire workflow lives at the endpoints and each service knows who to call next.

When to use which

  • Prefer orchestration when a single owner is accountable for the end-to-end process and you need central control, monitoring and error handling.
  • Prefer choreography when several autonomous participants need to interact but no one owns the whole flow, or when adding a central engine would create an unacceptable coupling.
