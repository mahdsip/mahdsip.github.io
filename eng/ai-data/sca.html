SCA

Service Component Architecture

SCA is considered a broader implementation of SOA than plain web services. The standardization body is OASIS. It provides an open, technology-agnostic model to build IT services as business functions and makes middleware capabilities more accessible to developers, letting components written in different languages work together.

Goals of SCA

  • Define a single model for providing and consuming services from any language.
  • Define a single way of assembling components together.

Assembly model

The SCA Assembly Model is a set of artifacts defined in XML. The base artifact is the Composite, which describes the details of a service and its calls to other services it may depend on.

Interoperability vs mediation

SCA offers interoperability instead of mediation (as in JBI) or invocation (as in JCA). It can wire an entire workflow without an intermediary because every endpoint knows the next one to call. This is not always the case in practice and an ESB is often used on top.

SDO

SCA usually goes hand-in-hand with SDO (Service Data Objects), a specification designed to simplify and unify data access across heterogeneous sources and formats. The goal is to work with a single API that can handle a database, an XML document, a web service and so on.

Implementations

The best-known implementations are Apache Tuscany (with Fabric3 as a production-ready implementation) and Service Conduit for Windows systems.
