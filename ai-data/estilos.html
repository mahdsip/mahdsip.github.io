Estilos y patrones de arquitectura software

Estilos teóricos y patrones prácticos con los que he trabajado

Aunque actualmente llevo unos años trabajando sobre la explotación de datos, durante mi carrera profesional he tenido el privilegio de poder trabajar con distintas arquitecturas como SOA, BPM, Cloud Computing o JAVA.

Han existido y existen muchas formas de clasificar los estilos arquitectónicos, diferenciables de los patrones de arquitectura en que los estilos son puramente teóricos mientras los patrones son puramente prácticos, pudiendo incluso mezclar varios de estos en una sola arquitectura.

Estilos arquitectónicos

Estilo de flujo de datos:

  • Tuberías y filtros (transformaciones de un stream de datos con un resultado final)
  • Proceso por lotes (batch y scripts)

Estilos centrado en los datos:

  • Pizarra o repositorio
  • BBDD
  • Hipertextos

Estilos de llamada y retorno:

  • Por capas (MVC)
  • Orientación a objetos
  • Por componentes

Estilos de código móvil:

  • Máquinas virtuales (código compilado)
  • Intérpretes (código interpretado)

Estilos heterogéneos:

  • Control de procesos
  • Basadas en atributos (razonamientos sobre atributos)

Estilos Peer2Peer:

  • Basados en eventos (Invocación de una función cuando se produce un evento Publisher/Subscriber)
  • SOA — Se hace una llamada a un servicio pasándole los parámetros necesarios y se espera un resultado. SOA 2.0 = SOA + eventos.
  • Basados en recursos. Los recursos se pueden descubrir a través de una URI y obtener su estado para operar con el recurso.

Cloud computing

  • Private cloud: La organización mantiene un mayor control sobre la infraestructura, la seguridad, la segmentación de red y el ciclo de vida de los servicios. Suele ser una opción razonable cuando hay requisitos fuertes de integración interna, cumplimiento, datos sensibles o necesidad de adaptar mucho la plataforma a procesos propios.
  • Public cloud: Se gana rapidez para provisionar recursos, elasticidad y acceso a servicios gestionados que aceleran bastante el desarrollo y la operación. El punto importante aquí es diseñar bien costes, observabilidad, seguridad y dependencia de proveedor para que la flexibilidad inicial no se convierta en deuda operativa.

Patrones de arquitectura

Los patrones de arquitectura son soluciones reutilizables y probadas a problemas recurrentes en el diseño de software. A diferencia de los estilos, son concretos y aplicables directamente. Los más habituales en el desarrollo moderno:

Singleton
Garantiza que una clase tenga una única instancia en todo el ciclo de vida de la aplicación y proporciona un punto de acceso global a ella. Muy usado para gestores de configuración, conexiones a bases de datos o caches compartidas. Su principal riesgo es introducir estado global que dificulta el testing y la concurrencia.

Factory / Abstract Factory
Delega la creación de objetos a métodos o clases especializadas, desacoplando el código cliente del tipo concreto que se instancia. Habitual en frameworks de persistencia y en la creación de componentes UI.

Observer / Pub-Sub
Define una dependencia uno-a-muchos entre objetos: cuando uno cambia de estado, todos sus observadores son notificados automáticamente. Es la base de los sistemas de eventos, las colas de mensajes y la programación reactiva.

Strategy
Encapsula una familia de algoritmos intercambiables detrás de una interfaz común, permitiendo variar el comportamiento en tiempo de ejecución sin modificar el código que lo usa. Muy útil en motores de reglas, validadores o pipelines de procesamiento.

Decorator
Añade responsabilidades a un objeto dinámicamente, envolviendo la implementación original sin alterar su interfaz. Base de los middlewares HTTP y de los interceptores en frameworks como Spring o Express.

Repository
Abstrae el acceso a la capa de datos detrás de una interfaz orientada a dominio, aislando la lógica de negocio de los detalles de persistencia (SQL, NoSQL, API remota). Fundamental en arquitecturas DDD y Clean Architecture.

API (Application Programming Interface)
Una API define el contrato mediante el cual los clientes externos consumen un servicio existente. El proveedor define la interfaz y la implementa. Es el mecanismo estándar de interoperabilidad entre sistemas: REST APIs, GraphQL, gRPC o las librerías de un SDK son todos ejemplos de API. Una API bien diseñada es estable, versionada y oculta los detalles internos de implementación.

SPI (Service Provider Interface)
La SPI es el patrón inverso a la API. El núcleo del sistema define una interfaz que terceros implementan para extender o reemplazar su comportamiento, sin modificar el código central. Es el mecanismo fundamental detrás de las arquitecturas de plugins y de la Inversión de Control (IoC).

Relación con la arquitectura:

  • Arquitectura de plugins: SPI permite que el núcleo de una aplicación permanezca intacto mientras terceros extienden su funcionalidad.
  • Inversión de Control (IoC): El sistema principal define la regla (la interfaz), pero la implementación concreta la proporciona un tercero y se carga dinámicamente en tiempo de ejecución.
  • Desacoplamiento estricto: Separa completamente a los proveedores de servicios de los consumidores, promoviendo el principio de responsabilidad única.

Diferencia clave: API vs. SPI

Concepto Propósito Quién lo define Quién lo implementa
API El medio para que los clientes consuman un servicio existente El proveedor del servicio El proveedor del servicio
SPI El medio para que los desarrolladores reemplacen o extiendan un servicio El núcleo del sistema o cliente El proveedor externo (terceros)

Ejemplos de uso comunes:

  • Java (JDBC): Java define la SPI para bases de datos (java.sql.Driver). Empresas como Oracle, MySQL o PostgreSQL implementan esa SPI para que sus drivers funcionen en cualquier aplicación Java sin cambiar el código fuente.
  • Sistemas de logs: Herramientas como SLF4J exponen una SPI para que puedas alternar entre proveedores de logs (Logback, Log4j) de forma transparente.
